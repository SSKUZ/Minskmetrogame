# Минское метро 2.0 — постоянные правила Work

Репозиторий: SSKUZ/Minskmetrogame. Godot 4.3. WEB ONLY.
Режим: ULTRA LOW WORK CONSUMPTION / SAVE FIRST / ZERO TESTING.

## Обязательный порядок

Разработка → сохранение в отдельной ветке GitHub → автоматический GitHub Actions → краткий ответ → остановка. Пользователь проверяет результат самостоятельно.

Экономия относится к организации работы, повторным операциям, тестированию, сборкам и ожиданию. Она НЕ разрешает сокращать необходимую разработку, упрощать архитектуру и реалистичность, пропускать детали или выполнять ТЗ частично. Полнота и качество конкретного задания обязательны.

## Разработка

- Читать только необходимые файлы; повторно использовать уже изученные материалы. Не проводить полный аудит без задания.
- Новая станция: использовать актуальный Station Base и его геометрию совместимости с V106; изучить ВСЕ предоставленные фото и видео, при необходимости найти дополнительные реальные материалы; восстановить пространственную структуру, платформу, потолок, колонны, стены, материалы, пол, освещение, лестницы, переходы, выходы, реальные надписи и указатели. Создать самостоятельный модуль и зарегистрировать его в существующем каталоге и меню просмотрщика. Не заменять реалистичную станцию схемой ради экономии.
- Доработка станции: исправить конкретное замечание, используя прежние материалы и необходимые новые фотографии; менять только нужные элементы, не переделывать всю станцию и не повторять полный анализ без причины.
- Для вагонов, кабины, пассажиров, тоннелей, депо, механики, управления и анимаций выполнять весь предусмотренный ТЗ объём с теми же требованиями к качеству.
- Не переписывать работающий код без причины, не создавать незапрошенные демонстрации, не менять посторонние модули. Переиспользовать существующие компоненты и реальные зависимости.
- Поиск референсов и чтение необходимых исходников разрешены: это часть качественной разработки, а не необязательная диагностика.

## ZERO TESTING

НЕ запускать игру, игровые сцены, тестовые сцены, браузерную версию, Playwright, Puppeteer, FPS-замеры, профилировщики, стресс-тесты и дополнительные тестовые сборки. НЕ делать скриншоты, записи видео, визуальные проверки и подробные отчёты о проверках. Не открывать опубликованный сайт для проверки.

НЕ выполнять локальный или ручной экспорт Godot. Обязательный импорт ресурсов и штатная сборка выполняются только в GitHub Actions и не считаются игровым тестированием. Исправление технической ошибки, непосредственно блокирующей экспорт или публикацию, разрешено при наличии такого задания/сведений; не искать её тестированием заранее.

## Ветки и совместимость публикаций

- Инфраструктурная основа ТЗ №52: `feature/metro2-automated-module-deploy`. Пока пользователь не интегрировал её в main, новые ветки создавать от этой основы либо от более свежего совместимого исходного коммита уже опубликованного нужного модуля, содержащего эту инфраструктуру. Наличие правил в одной ветке не означает их автоматического появления в старых ветках.
- Автоматический режим: `feature/metro2-auto/<ID-пакета>/<задача>`. Например `feature/metro2-auto/borisovsky_trakt/lighting` или `feature/metro2-auto/institut_kultury/new-station`.
- Общие изменения, затрагивающие несколько независимых пакетов: отдельная совместимая ветка `feature/metro2-auto/integration/<задача>`. Не сливать несовместимые ветки автоматически.
- Использовать актуальный исходный коммит нужного модуля из `module-deploy-state.json` ветки gh-pages, если он там есть. Не начинать новую доработку модуля от старой версии, исключающей его уже опубликованные изменения.
- Старые workflows сохранены для возврата; их исторические ветки не входят в новый автоматический шаблон. Не запускать оба способа для одного изменения. Если пользователь явно задал старую ветку, сохранить его выбор и перенести необходимую инфраструктуру без включения второго параллельного автозапуска.
- Реестр сцен: `metro2/modules/core/module_catalog.gd`. Реестр опубликованных пакетов и зависимостей: `metro2/module-viewer/module-packs.json` и `pack-resources.json` в gh-pages. Не дублировать их отдельным перечнем станций. `metro2/config/module_deploy_manifest.json` задаёт только контракт публикации и исходные контрольные версии.
- Для новой станции добавить её существующими средствами в каталог сцен и меню `metro2/viewers/module_viewer.gd`. CI обнаруживает новый ID и каталог модуля; не создавать новый просмотрщик. Название берётся из меню, зависимости — из исходников и текущего реестра пакетов.
- Новые двоичные ресурсы сохранять восстанавливаемо. Для GLB, сохранённых частями, поддерживаются `parts/manifest.json` с filename/size/sha256/parts[].name и проверка целостности при штатном восстановлении в CI. Если формат иной, адаптировать восстановление в пределах задания; не упрощать модель.

## Сохранение и публикация

- После логически законченного существенного этапа сохранять результат в GitHub; не оставлять готовую работу только во временной среде. При ограничениях времени/лимитов сохранить имеющиеся существенные изменения прежде необязательных действий.
- На отдельную ветку, изменения в пределах ТЗ, коммиты, обычный push и автоматический GitHub Actions разрешение предоставлено заранее. Не запрашивать его повторно.
- Не удалять значительные данные, не перезаписывать чужие ветки, не делать force-push, merge в main или изменение прав доступа без отдельного разрешения. Не добавлять секреты в исходники.
- GitHub Actions сам определяет изменённые модули, выполняет импорт и упаковку только нужных пакетов. Общие зависимости обновляются вместе с затронутыми пакетами, а не искусственно отделяются от них.
- Публикация сохраняет остальные файлы gh-pages, сливает только метаданные выбранных пакетов с актуальной публикацией и отказывается заменять более свежую несовместимую версию. Конфликт требует интеграции исходников, а не принудительного обхода защиты.
- Постоянный адрес: https://sskuz.github.io/Minskmetrogame/metro2/module-viewer/ . Не менять настройки камеры, управление, интерфейс и адрес без необходимости задания.
- После push НЕ запускать публикацию вручную, НЕ ждать GitHub Actions, НЕ опрашивать её статус и НЕ проверять опубликованный сайт. Дать ссылку на workflow с фильтром ветки (либо уже известный запуск) и постоянный адрес, затем остановиться. Документация и материалы разбора сами по себе не вызывают сборку игры.
- Не заявлять об успешной публикации, если это не подтверждено уже доступными сведениями; достаточная формулировка после push — «изменения сохранены; сборка запускается автоматически».
