# Спецификация будущего пассажирского адаптера v106 — ТЗ №1.2

**Статус: проект интерфейса. Не готовый layout для передачи в конструктор.** Измеренные anchors и кривые находятся в V106-COMPATIBILITY-TZ1.2.json. Поля `hipHeight=null` намеренно не проходят валидацию старого layout, пока не проверен пассажирский скелет. Исходная система не изменена.

## 1. Рамки и непрерывность перехода

Для первой интеграции — прямой горизонтальный путь, обслуживаемая сторона −X, world/track frame совпадают, platform.position.y=0. Вагон и пассажиры используют один railHead datum. `train.floorY=1.1805`, `platform.y=1.1805`. Сам `platform`-объект для API расположен на railHead, а не своей верхней поверхности: иначе worldPosition дважды добавит высоту.

Координаты сидений/дверей/агентов в поезде — канонические S из JSON. `train.offsetZ=trainFrontZ`; `platform.position.z=stationOriginZ`; **context.dist=train.offsetZ-platform.position.z**. Это локальная разность рамок, не полный пробег маршрута. При посадке существующий код делает `a.z-=dist`, при высадке `a.z+=dist`: мировая Z обязана оставаться неизменной в момент смены пространства. Для всех 16 дверей проверить равенство до/после с допуском 1 мм на трёх положениях остановки −0,5/0/+0,5 м. Обновление offset и context должно быть атомарным; нельзя подменять новое значение в старом frame посреди обмена.

В первой версии поворот/смещение X/Y станции не поддерживается старым PassengerSystem.worldPosition. Повернутая или поднятая станция потребует адаптации потребителя. Расширенный StationDefinition хранит полные матрицы уже сейчас; runtime обязан явно отклонить неподдерживаемую ориентацию.

## 3. Предлагаемые точки движения

Для каждого проёма использовать его S и измеренный thresholdX. Поперечные значения ниже — Б, проектные предложения, а не измерения станции:

| Поле legacy layout | X, м | Назначение |
|---|---:|---|
| thresholdX | −1,3005 | Измеренная наружная грань пластины |
| entryX | −1,270 | Промежуточная точка перехода в вагон |
| insideX | −0,400 | Конец перехода; далее через aisleX=0 |
| exitInnerX | −0,900 | Подход к порогу из вагона, только в дверном коридоре |
| exitOuterX / exitClearX | −1,850 / −2,150 | Выход и освобождение дверной полосы |
| approachX / queueX | −1,850 / −2,150 | Ожидание готовности/боковые очереди |
| yieldBoundaryX / yieldX | −2,300 / −2,750 | Уступание потоку |

Точки вне острова или на колонне отклоняются; не применяется молчаливый clamp, который перенесёт всех к одному месту. Центральную полосу высадки задавать по ширине проёма и капсулы; очереди размещать по ±S за её пределами. Старые ранговые отступы 1,28, 0,65 и поперечное 0,35 — параметры будущей проверки вместимости, не доказанные отступы Малиновки.

Подключение `doorsSafeToClose` должно учитывать **отдельно** свободный проход и объём движения створок. В старом коде `halfWidth` используется и для навигации, и для детектора препятствий. Одно значение 0,590 не описывает всю протяжённость движущихся створок. Будущему адаптеру/потребителю нужны passageWidth, leafSweptVolume и obstructionEnvelope; разрешение закрытия только при свободном пути и завершённом обмене. До расширения не считать готовой безопасную интеграцию.

## 4. Сиденья и стоячие зоны

В JSON выгружены **168 физических центров подушек**: 40/44/44/40. Их X=±0,962, верх в канонической рамке Y≈1,7055, то есть 0,525 м над основным полом. Это не 168 готовых пригодных мест симуляции: ширина людей, ноги, анимация, группы и фактическая доступность проверяются отдельно.

`seatAnchor`: устойчивый id, x/z из mesh, `heading=+π/2` для левой стороны и `−π/2` для правой, approach=(side*0,400; S сиденья). Направление проверить по forward-axis модели человека. `hipHeight` получить калибровкой скелета, чтобы таз/ягодицы опирались на верх подушки; автоматически копировать 0,53 из fixture нельзя. Визуальная проверка нужна на взрослом, ребёнке и широком профиле.

Резервирование старой системы считает соседнее место занятым при расстоянии <0,58 м. Реальный минимальный шаг подушек v106 — **0,435 м**, у шестиместных секций около 0,475 м. Это заблокирует часть соседних сидений. Будущая минимальная доработка: занятость по `seat.id`, соседство по `adjacentSeatIds`, ограничение геометрического пересечения людей отдельно. Семейный поиск с условием 0,58…0,75 м также надо заменить реальным соседством.

Для первой проверки предложить aisleX=0, полосу центров по X=±0,400, с учётом размера капсулы; основной поток по X=0. Салонные продольные интервалы **до дополнительного отступа**:

- car0: S=2,003…19,033;
- car1: S=20,176…39,042;
- car2: S=40,182…59,048;
- car3: S=60,191…77,221.

Эти интервалы исключают кабины/торцы на уровне floor construction; это ещё не полный navigation mesh. Кандидаты стоячих мест: X=±0,270, сетка S с шагом 0,650, отступ от торцов не менее 0,350. Затем обязательный фильтр: дверные полосы, seat approach, реальные стойки, багаж, межличностные расстояния и места семьи. Плотность/вместимость определяется после фильтра, а не по количеству клеток. Не генерировать стоячие места на плите кабины.

В PassengerBoardingController встречается очередь `aisleX±0,71`: при радиусе человека 0,24 её внешний край достигает 0,95 м и заходит в сиденья (их внутренняя грань около 0,731). Простое уменьшение navigationZone этот фиксированный путь не исправит. Требуется отдельное изменение генератора внутрисалонной очереди с проверкой свободных мест и капсул.

## 5. Поручни

Экспортированы осевые кривые исходных TubeGeometry, отобранных по идентичности геометрии с saloonRails, и продольные цилиндры 714: 94/66/66/94, всего 320. В числе этих кривых есть перемычки и потолочные детали; это не 320 доступных человеку хватов. У каждой — радиус, car/id, controlPoints/тип кривой либо endpoints цилиндра, в канонических координатах. Эти данные получены **до batching** без изменения mesh, затем преобразованы матрицей нужного вагона.

Существующий readCarriageRails обходит TubeGeometry; после batching часть таких геометрий исчезает, а длинные CylinderGeometry он вообще не читает. Поэтому будущий адаптер подаёт `gripAnchors` из sidecar-профиля, не надеется на обход финального mesh. На кривой воспроизвести 129 точек getPointAt по тем же CatmullRom-параметрам; для прямого цилиндра — линейные отсчёты. При движении точки преобразуются в ту же world frame, что и плечи/руки пассажира. Старые UUID заменить устойчивыми профильными ID. Отбор по досягаемости, направлению кисти и возрасту сохранить.

## 6. Колонны, выходы и жизненный цикл

Footprint каждой колонны берётся из архитектурного модуля с кольцом/цоколем. Для старого API возможна консервативная окружность, перекрывающая весь footprint; итоговый маршрут проверяется со swept capsule. Нельзя проверять только конечную точку маршрута. Для сложных скульптур допустима группа консервативных примитивов; потеря прохода должна приводить к ошибке компоновки, а не проходу сквозь опору.

StationDefinition хранит `exits[{id,level,entryPolygon,landingAnchor,routeId,direction}]`, spawn zones и связи. В текущем departurePath exit вычисляется через PLATFORM.minX+8,3 и торцевые Z с поправками от ID. Это не интерфейс к настоящим лестницам: нужен согласованный будущий потребитель exit graph. Географический выход обоих торцов Малиновки пока не восстановлен, поэтому соответствующие реальные anchors остаются null с запретом production activation.

Обычная остановка: 80–100 на платформе, около 30–40 входящих при наличии мест, распределение по всем 16 дверям. Конечная: только высадка, сохранение личности до физического выхода, 0 оставшихся внутри. Подтверждения `passengerExchangeComplete` и `doorsSafeToClose` обязательны, ограничение времени не удаляет человека из вагона.

## 7. Условия подключения

Нужно передать реальные seats, standing zones, navigation/collision zones и gripAnchors, затем проверить группы, сохранение идентичности и конечную. Без согласования перечисленных изменений потребителя возможен только **контрактный стенд и геометрические anchors**, а не завершённая пассажирская интеграция. Пассажирская система в этом checkpoint неизменна.
